## Preview and apply the skill refresh

Use an initialized native profile, the matching checkout and an executable native core. Build the desktop source first so the CLI can use its compiled state-hash implementation:

```sh
npm --prefix desktop-shell run build
```

Create a read-only plan. These are placeholder paths for the intended profile; the output must be a new file outside every Git checkout:

```sh
node scripts/refresh-company-setup.mjs \
  --profiles company/setup-profiles.json \
  --core /absolute/path/to/atlas-core \
  --user-data-path /absolute/private/daftar-profile \
  --output /absolute/private/company-setup-preview-20261125.json
```

Preview reads existing state directly, without calling the native core, initializing state or changing employees. Plans contain private employee identities and belong in the private workspace. Standard output contains aggregate counts only.

Apply the authorized change to the same intended profile:

```sh
node scripts/refresh-company-setup.mjs \
  --profiles company/setup-profiles.json \
  --core /absolute/path/to/atlas-core \
  --user-data-path /absolute/private/daftar-profile \
  --output /absolute/private/company-setup-apply-plan-20261125.json \
  --apply
```

Apply rereads the current native snapshot and builds a fresh plan; it does not blindly replay the preview. The optional output file contains that plan, while standard output reports aggregate application counts. Retain the existing workspace backup and use a single intended writer during the migration.

### Preservation and recovery

- Existing skill order and custom references are preserved; missing references are appended.
- Paused employees remain paused. Fired employees are skipped. Names, roles, ownership, grants, budgets and existing work remain unchanged.
- Complete-plan validation checks skill files, ownership, duplicates, receipt capacity and the native 20-skill limit before the first update.
- Each employee transaction checks the current state hash. A concurrent edit stops the operation instead of being overwritten.
- The sequence is additive and restartable, not one transaction across all employees. After an interrupted response, inspect current state and prepare a fresh plan; the previous command may already have committed.
- Reapplying an unchanged accepted profile adds no duplicate skills. A zero-change plan is valid.
- Local application still requires the paired desktop's normal synchronization before reporting the live website updated.
